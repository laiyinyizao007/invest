# ADR: 账户级风控——双层熔断、平仓永远放行、紧急平仓只在确认安全时才重试

- 状态:已采纳
- 日期:2026-11-09
- 跟踪:Issue [#1](https://github.com/laiyinyizao007/invest/issues/1)
- 实现:`risk/account_guard.py`、`risk/order_policy.py`、`trading/guard_rule.py`、`trading/safe_risk.py`

## 背景
策略层风控(单笔预算、移动止损)只管一个策略,且只在回测里验证过。1 万元账户需要一个**账户级、独立于策略**的最后防线,
并且这道防线自己不能成为风险来源(比如把平仓也拦住,或者重复下单)。

## 决策

### 1. 双层熔断(用户口径,权益口径含浮动盈亏)
| 层 | 触发 | 动作 |
|---|---|---|
| 当日熔断 | 账户权益较**当日开盘权益**下降 ≥ 600 元 | 当日禁止新开仓;撤销未成交开仓单;紧急平仓;次交易日自动解除 |
| 累计死线 | 账户权益距**历史最高权益**回撤 ≥ 2000 元 | 永久锁定;撤单并紧急平仓;**确认空仓后**发硬锁定事件并退出;必须人工解锁 |

- 累计口径取"距最高点回撤",账户从 1 万元起步时等价于跌破 8000 元,账户创新高后底线随之抬高。
- 当日开盘权益取**前一次采样的权益**(持久化),而不是新交易日第一次采样:进程在已经亏损后的盘中重启时,
  若以第一次采样为基准,当日熔断会被抬高而永远不触发。
- 权益 ≤ 0 或 NaN 视为无效采样(CTP 启动/查询瞬间常报 0),不触发也不污染最高点。
- 锁定状态原子写盘(含 fsync),重启后不丢;状态文件损坏时保守地按硬锁定处理。

### 2. 平仓永远放行
- `AccountGuardRule.check_allowed` 对任何平仓委托返回 True;
- `SafeRiskEngine` 让平仓单跳过 vnpy_riskmanager 的**计数类规则**(每日上限、活动委托数、重复报单)。
  这些规则不区分开平,触顶后会把保护性平仓也拦下,而持仓还在。平仓仍要通过合约存在、价格为最小变动价位整数倍、单笔大小等合法性检查;
- 紧急平仓走原始发单通道,绕过全部风控规则。

### 3. 废单与重试("软硬分离"的收窄版)
用户提出:硬拒绝 0 次重试并熔断;软拒绝(网络抖动)最多 3 次、1/3/5 秒重试。采纳,但做了收窄:
- **开仓单永不自动重试**:策略下一根日线会自己重新判断;重发有重复下单风险。
- **网络抖动时订单可能已被接受**(回报丢失)。因此任何重试前必须**观察到**上一轮每笔委托处于终态且未成交;状态未知绝不重发,超时升级人工。
- 重试只用于**紧急平仓单**:首次 + 最多 3 次重试(间隔 1/3/5 秒),用尽后升级为硬故障并告警。
- 废单原因按文本关键词分类,**未知一律按硬拒绝**。CTP 的真实错误文本需在 SimNow 上故意触发各种错误后采集;不凭记忆写错误码。
- CTP 先推委托回报、后写错误日志,所以分类延迟 1.5 秒,在前后 3 秒窗口里取最近的错误日志。
- 开仓被硬拒绝,或 10 分钟内 3 次软拒绝 → 当日禁止开仓。平仓单被拒只告警,绝不锁定(离场不能被阻止)。

### 4. 紧急平仓状态机的防重复下单设计
- 按**成交量**对账,而不是反复读取 OMS 持仓:CTP 持仓回报约每 2 秒才刷新一次,成交后 OMS 里仍是旧持仓;
- 成交量已覆盖目标持仓但持仓回报不清零 → 主动查询持仓并等待,超时升级人工,**不重发**;
- 当日熔断的平仓失败后,随后的硬锁定要重新开一轮平仓,不能被卡死的旧状态吞掉;
- 上海/能源中心合约被冻结的仓位使拆分器返回空时,告警并计入重试,不当作已发出。

### 5. 硬锁定后的进程行为
- 平仓**已确认空仓**:发出硬锁定事件,运行时正常退出(退出码 0,容器不会自动重启);
- 平仓**失败**:进程**保持存活并持续告警**,不退出。因为 vn.py CTA 的止损单是引擎本地触发的,**带着持仓杀进程会让持仓失去止损**。
  (用户原方案是"直接抛异常强制结束进程",此处修正为先平仓、确认空仓再退出。)
- 启动时若状态文件里已是硬锁定:告警后直接退出,不连接、不交易。解锁用 `scripts/unlock_account.py`(需输入 `UNLOCK` 确认)。

## 已知局限
- 交易日判断按周末顺延,**不处理法定节假日**;长假前后的当日熔断边界需人工留意。
- 回撤口径含浮动盈亏,未计手续费以外的资金流水(出入金会被当成盈亏——出入金前后应先停机)。
- 净持仓(`Direction.NET`/`Offset.NONE`)模式未支持。**2026-11-11 起 fail-closed**(Issue #10,`risk/positions.py`):账户若回报方向不明的持仓,
  启动对账与运行中漂移检测拒绝/告警,紧急平仓**不猜方向**、直接升级人工(此前按"非多即空"计算,NET 会被当空头算反、平反)。
  账户是否真会回报 NET **尚未实测**(`docs/modules.md` 称 SimNow 默认净持仓账户,`drill.py` 已单列处理 NET)——SimNow/国信测试环境验证后在此补记结论,再决定是否做真正的净持仓支持。
  codex 审查(2026-11-11)指出的**未解决局限**(如实登记,本次不改状态机):
  - **空仓启动证明不了账户形态**:启动对账只能检查已存在的持仓;净持仓账户空仓启动会通过对账,策略开出第一笔仓后才出现 NET,经 `drift_tolerance_seconds`(默认 15 秒)判定漂移并触发紧急平仓——平仓因方向不明而升级人工。
    即 fail-closed 发生在**风险已经敞口之后**。真正的解法是把"持仓模式"做成显式的部署/账户不变量(配置项 + 实测核对),待实测结论出来再做。
  - **失败的紧急平仓不会自动恢复**(既有行为,非本次引入):`_escalate_flatten` 置 `failed` 后 `_advance_flatten` 不再观察持仓;人工平仓后不会发 `flat=True`,硬锁定下的运行时也不会自动退出,且告警是一次性的。
    改动涉及状态机,放进路线图(失败态继续观察持仓、确认空仓后发 `flat=True`、限频重复 FATAL 提醒),不在本批动。
  - **取舍:混合持仓整体升级人工**:账户里只要有一笔方向不明的持仓(哪怕其它持仓方向明确),紧急平仓就一笔不发——账户形态不明时对"已知"的那部分自动平仓同样不可信。
    代价是硬锁定时已知方向的仓位也留给人工处理;有测试锁定该行为(`test_mixed_directed_and_undirected_positions_send_no_close_orders`)。
  - 已补的纵深防御:`_send_close_orders` 自己也对方向不明的持仓拒绝发单,不依赖调用方的前置检查;升级人工前**先撤掉已挂出的平仓单**(状态机升级后不再观察,不能让它们在交易所无人监督);
    `describe` 对 `direction=None` 不抛异常。`scripts/drill.py` 仍有一份自己的净额计算,批 B 并入 `risk.positions.signed_net`。
- 多账户时用 `account_id` 指定;未指定则取第一个。
