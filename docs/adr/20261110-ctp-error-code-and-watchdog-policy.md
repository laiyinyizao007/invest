# ADR: CTP 错误码优先的废单分类、假死强撤与断线状态机(极限压力测试前置改造)

- 日期:2026-11-10
- 状态:已确定,随本次代码同一原子提交
- 相关:`20261109-account-risk-lock.md`、`20261109-use-vnpy.md`、`docs/reject-texts-simnow.md`

## 背景

为混沌工程四个极限演练(拔网线、废单轰炸、假死看门狗、600 元断头台)做前置改造时,
首先纠正两个前提:

1. **vn.py 4.5 的 `BaseGateway` 不存在 `on_error` / `on_disconnected` 回调**。它只暴露
   `on_event/on_tick/on_trade/on_order/on_position/on_account/on_quote/on_log/on_contract/write_log`。
   CTP 的错误与断线全部以 `EVENT_LOG` 文本到达;vnpy_ctp 的 `write_error()` 实际调用 `write_log()`,
   即拒单错误是 **INFO 级别**文本(如「交易委托失败，代码：21，信息：…」)。
2. 仓库里没有 `global_risk_manager.py`;熔断由 `risk/account_guard.py` 与 `trading/guard_rule.py` 承载,
   600 元当日熔断(断头台)此前已完整实现,本次不改其逻辑。

四个演练盘点后只有三处真实缺口:废单分类只认关键词不认数字错误码、假死看门狗只告警不撤单、
断线没有显式的分通道连接状态与「无积压补发」证据。

## 决策一:废单三级分类(错误码 → 关键词 → fail-closed)

`risk/order_policy.py` 新增 `extract_ctp_error_code()` 与 `CTP_ERROR_KIND` 码表,
`classify_reject()` 签名不变,内部分三级决策:

1. 文本带「代码：N」且 N 在码表内 → 直接按码表定论;
2. 无码或码未收录 → 回退原有 HARD/SOFT 关键词分类;
3. 仍无法识别 → 一律 HARD(宁可停手也不重试)。

收录的码(只认 SimNow 实测或官方错误码表背书,不凭记忆写码):

| 码 | 含义 | 分类 |
|---|---|---|
| 21 | 资金不足/保证金不足;SimNow 实测非交易时段也回 21(席位未连接交易所) | HARD |
| 81 | 价格超出涨跌停/价格非法 | HARD |
| 63 | 权限不足/未授权 | HARD |
| 32 | 报单字段非法 | HARD |
| 33 | 合约交易状态不允许 | HARD |
| 14 | 合约不存在 | HARD |
| 30 / 31 | 报单已撤销 / 已成交(状态过期,不得盲目重发) | HARD |

**软错误码表刻意留空**:没有实测样本前不写码;软拒绝仍由 `SOFT_KEYWORDS` 文本路径识别,
新样本经 `scripts/collect_reject_texts.py` 采集后再补表。

码表优先的直接动机:实测文本「代码：21…该交易席位未连接到交易所」含软关键词「连接」,
纯关键词方案存在歧义;错误码 21 明确是硬拒绝(重试不会变成可成交)。

正则锚定「代码」前缀(`代码[:：]\s*(\d+)`,兼容全/半角冒号)且只取首个数字码,
避免把断线原因 `reason` 里的数字误当成错误码。

**本地返回码与柜台错误码不混用**:`CtpTdApi.send_order` 在 `reqOrderInsert` 本地失败时
返回空串并写「委托请求发送失败，错误代码：-3」,负码(-1 网络失败 / -2 未处理请求过多 / -3 流控)
是本地 API 返回值,不产生 `OrderData`、不走废单分类链路,因此不进 `CTP_ERROR_KIND`;
其「不排队、快速失败」的语义由 `tests/test_disconnect_signal.py` 单独锁定。

硬拒绝的告警升级为 FATAL「严重错误,已停止策略开仓」并带错误码与原因;平仓拒单路径不变
(只告警、永不锁离场),措辞里不得出现「已停止」。

**FATAL 只在锁定状态真实转换时发一次**:废单分类有 1.5 秒延迟,窗口内可能有多笔在途单陆续被判 HARD。
第一笔硬拒绝完成「锁定 + 撤全部开仓单 + FATAL」后,后续硬拒绝只保留 ERROR「委托被拒」留痕,
不再重复 FATAL(codex 第八轮审查动态复现:旧实现会刷出多条声称「已撤销全部挂单」但实际无单可撤的 FATAL)。

## 决策二:假死看门狗首次越限强撤开仓单

交易时段内超过 `tick_stale_seconds`(默认 60s)无 Tick:

- 旧行为:周期 WARN「行情停更」(300s 节流),只告警;
- 新行为:首次越限边沿触发 ERROR「行情假死」并经规则**唯一公开入口**
  `AccountGuardRule.cancel_open_orders_on_stale_tick()` 撤销全部活动**开仓**委托;
  新 Tick 到达复位边沿,允许下一次假死再次触发;周期 WARN 保留。
- `RuntimeConfig.stale_cancel_open_orders`(默认 True)一键回退到旧的只告警行为。

互斥保证:撤单复用规则私有 `_cancel_all_open_orders()`,它按 `CLOSING_OFFSETS` 过滤,
平仓单与 `FLATTEN_REF` 紧急平仓单天然不在撤销集合内,因而不会与紧急平仓状态机竞争
(不会撤掉刚重发的平仓委托)。定时器线程与规则定时器同属事件引擎串行调度,无并发改写。

**休市时间不计入静默与挂单年龄(codex 第八轮审查修复)**:`_last_tick` 是单调时钟时间戳,午休/夜盘休市期间
没有 Tick 本属正常;若不按时段边界重新武装,开盘后定时器先于本时段首 Tick 触发时会把整个休市时间
(实测复现 7261s)误算成静默,对年龄 0 秒的新挂单也误报假死并强撤。因此运行时在「非交易→交易」时段
边沿把 `_last_tick` 置 None、解除假死边沿,等首 Tick 后才开始计 60s;初始基线在 `start()` 记录,
首个定时器不被当成边沿。规则自身的 120s 开仓委托超时是同类问题:运行时把时段判定注入
`AccountGuardRule.session_active`,休市期间不做超时撤单,时段重入时把在跟踪挂单的计时起点拨到开盘时刻;
重入时对撤单节流表 `_cancel_requested` 的清理只覆盖开仓单 id,平仓/紧急平仓撤单的 10s 节流不被休市边沿清掉
(防止未来出现短于 10s 的时段间隙时平仓撤单绕过节流)。规则的时段基线在运行时注入时同步,与运行时共用同一判定函数。

## 决策三:断线连接状态机与「无积压补发」证据

`TradingRuntime` 维护交易/行情两条通道各自的连接状态(未知/已连接/断开),
由精确措辞驱动迁移:

- 「交易服务器连接断开」「行情服务器连接断开」→ 对应通道断开(边沿,重复日志不重复告警);
- 「交易服务器登录成功」「行情服务器登录成功」→ 对应通道恢复;
- 「连接成功」但未登录的中间态**不**驱动状态,避免「连上→未认证→再断」期间告警抖动;
- 他网关日志不影响状态(同网关过滤)。

状态经只读属性 `connection_state` 暴露,供演练(`scripts/drill.py`)与外部巡检读取。

「重连后不会一窝蜂补发」不是靠状态机保证的,而是两条既有机制的组合,本次用离线测试固化为证据:

1. 框架层:`CtpTdApi.send_order` 断连即本地失败返回空串,**没有订单队列**;
2. 策略层:`pending_entry` 在发出前就置 None,一次性消费,发不出去也不重试,等下一根日线重新判断。

`tests/test_disconnect_signal.py` 用 `FakeGateway` 的 `disconnected` 模式复现整条链路;
`scripts/drill.py` 的 disconnect 场景增加连接状态、窗口内发单失败告警计数与「无积压补发」证据项,
现场演练看现象,离线测试锁语义。

## 已知边界

- 错误码措辞随 vnpy_ctp 版本可能变化;码表与标记措辞均以 SimNow 实测文档
  (`docs/reject-texts-simnow.md`)为准,升级 vnpy_ctp 后需回归 `tests/test_account_guard.py`。
- 假死强撤只处理挂单,不自动平仓:行情停更时本地止损本就无法触发,撤单是为了消除
  「无人看守的挂单可能在恢复瞬间成交」的风险;持仓去留仍由既有熔断/人工流程决定。
- 连接状态只反映日志文本驱动的认知,不主动探测;CTP 原生 API 的自动重连机制不变,本决策不替代它。
