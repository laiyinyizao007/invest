# ADR: 会话内哈希回贴批准(批准摩擦优化,Issue #59 方案 A)

- 状态:已采纳(2026-11-20,用户确认)
- 关联:`20261113-dsh-research-entry-and-out-of-band-approval.md`(第 2 条「批准必须带外」——本 ADR **有意修订**它的一小部分)、`20261114-consequence-domain-tiers.md`(本改动判**执行域**:涉事 5 文件全部不可降级,`tools/check_domain.py` 实测)
- 触发:用户反馈「批准太麻烦」。原流程要求人去浏览器里的一次性批准页输完整 sha256;用户在了解风险后选定方案 A(会话内两阶段),并**明确接受**其削弱(原文:"我接受风险"、"直接改,这是研究方案,不是实盘")。

## 背景

批准账本(`data/research-control/approvals.json`,链式 + 锚点)的三条既有写入路径都要求「人到现场」:
带外批准页(127.0.0.1 一次性网页,输完整 64 位 sha256)、CLI `approve`/`review`/`--confirm-reviewed`(交互式终端 + 粘贴哈希)。
模型通道里的哈希、批准页 URL、批准命令一律被 `scrub_text` 擦掉——这是围住 codex 第 2 轮实测复现的
「模型自我批准」Critical 修出来的防线。

摩擦点:批准页要人切浏览器、抄哈希、粘贴;每轮迭代候选一改就要重批。

## 决定

`request_approval` 增加两阶段 **inline 模式**(默认),页面模式(`mode="page"`)原样保留:

1. **第一阶段**(`confirm_sha256` 缺省):会话/候选校验(仍只认当前会话本轮的候选)→
   静态筛查(**不过连哈希都不发**,与 CLI approve 同一前置)→ 返回:候选文件名、
   `pending_strategies` 相对位置、该文件当前内容的 **sha256**、操作指令。
   **返回值不含源码**——人应在本机编辑器里打开盘上的候选文件通读;聊天里经模型转述的
   内容不可作为审阅依据。这比原设计草案(源码进会话)更保守:展示内容不经模型之手,
   人读到的就是将要执行的字节。
2. **第二阶段**(带 `confirm_sha256`):格式校验 → `secrets.compare_digest` 常数时间比对
   服务端**自算**哈希 → 一致则经 `record_approval(..., sha256=<自算值>, via="inline-chat")` 落账。
   落账哈希用服务端自算值而非回贴值;`record_approval` 内部还会再重算文件哈希——
   **批什么 = 盘上什么文件**,这条绑定不经模型之手。

账本条目新增 `via` 字段(`page` / `cli` / `inline-chat` / 旧条目缺省视为 `legacy`),
只进链式 seal 载荷供审计,不参与任何判定;dashboard 研究区增量展示通道计数。
脱敏豁免:**只**放行 inline 返回值里的哈希这一个值(占位符替换后过 `redact_for_model` 再换回),
其余规则(路径/批准页 URL/批准命令/凭据)照旧全洗;页面模式的 URL/哈希照旧不进模型通道。

## 明确接受的削弱(用户 2026-11-20 确认)

1. **人审的展示面**。第一阶段只发哈希与位置,源码由人自己从盘上读——展示面不经模型之手
   (这是对原草案的收紧);但「人是否真的读了」仍然只是程序性纪律,无法技术强制。
2. **模型可自我完成回贴**。模型自己算哈希、自己调第二阶段,没有任何技术障碍。
   必须如实记录:这个缺口**不是本次新增的**——日常 Desktop profile 里模型有终端 +
   `danger-full-access`(用户 2026-11-19 明确接受),`research_api.py` 的注释自己承认
   TTY 校验可伪造(`CREATE_NEW_CONSOLE` / `pty.spawn`);带外批准页的「模型够不着」前提
   在该环境下本来就不成立。本次只是把这条既有现实**从暗处挪到明处**,并给了它一个
   审计标记(`via=inline-chat`)。
3. **不变量修订**。`tests/test_research_boundary.py` 两条「MCP 无写路径」不变量改写为
   「写路径恰好一个、必带 via、必先常数时间比较」;判定器(`_record_approval_call_lines`)
   原样复用——出现 `getattr(rs, "record_" + "approval")`、`__dict__` 下标等第二扇门,
   调用点计数超 1 即红。

## 保留不变的东西

- `record_approval` 仍是**唯一**写入者(锁、核链、原子替换、哈希重验都在那一边);
- 批准绑定内容哈希:代码改一个字节,批准即失效(所有消费者重验);
- 只能批准当前会话本轮的候选;静态筛查前置;账本损坏 fail-closed;
- 页面与 CLI 批准行为逐字节不变(回归测试盖住);网关 403 语义不变;
- 实盘准入线(`promotion_approval.json` / `live_admission` / `promotion_gate`)不涉及。

## 备选方案(未采纳)

- **B:终端一键化**(不碰写路径):摩擦略高,保留作严格通道(页面/CLI 仍在)。
- **C:A+B 都做**:改动量翻倍,页面与 inline 覆盖同一场景,收益边际小。
- **简化哈希输入(短哈希)**:一律不做——输入长度是「人真的看了」的最后一块仪式性锚,
  削它省不了几秒,却直接削绑定强度。

## 后果

- 研究迭代的批准摩擦从「切浏览器 + 抄哈希」降到「编辑器看代码 + 会话里粘贴哈希」。
- 审计面变好:批准通道首次可区分(`via`),dashboard 可见。
- 遗留登记:严格场景(不受信任的研究会话)仍应使用页面模式或专用 research DSH_HOME
  (`start-research-dsh.ps1`),那里模型没有终端能力,带外屏障完整成立。
