## 由这几轮采集发现的真实缺陷(已修)

1. **vnpy_ctp 的 `write_error()` 实际调用的是 `write_log()`**,也就是拒单是以 **INFO 级别**写出来的:
   ```
   vnpy_ctp/gateway/ctp_gateway.py:221
   def write_error(self, msg: str, error: dict) -> None:
       log_msg: str = f"{msg}，代码：{error_id}，信息：{error_msg}"
       self.write_log(log_msg)      # ← write_log,不是 write_error
   ```
   我们原来的 `guard_rule._on_log` 只收 `log.level >= ERROR`,**永远收不到拒单文本** →
   废单分类一律拿不到原因 → 全部按硬拒绝 → 紧急平仓单的有限重试永远用不上。
   已改为按文本特征识别(`REJECT_LOG_MARKERS`)。
   `trading/runtime.py` 的网关错误告警同样漏,一并修。

   **措辞必须精确**:收窄到 `("交易委托失败", "交易撤单失败")`。宽泛的"失败"会把
   "行情服务器登录失败""行情订阅失败""委托请求发送失败"也收进来——那些不是废单原因;
   一旦真废单的日志迟到或缺失,就会拿无关文本去分类,把可重试的软拒绝误判成硬拒绝。
   `runtime.py` 的告警用另一组宽措辞 `GATEWAY_ERROR_MARKERS`(只是给人看,分类错误没有后果)。

2. **实测文本的关键词冲突**:`该交易席位未连接到交易所` 含"连接"(软关键词),但它是硬拒绝。
   已作为硬关键词显式列出。

3. **假网关的级别失真**:`tests/fakes.py` 原先用 ERROR 级别发拒单日志,掩盖了上面的缺陷。
   已改为 INFO 级别,与真实 CTP 一致。

4. **采集脚本的竞态(第一轮白跑一趟的直接原因)**:
   vnpy_ctp 的 `onRspOrderInsert` 是**先** `gateway.on_order(order)`(订单回报)**后**
   `gateway.write_error(...)`(错误日志),见 `ctp_gateway.py:503-522`。事件引擎按 put 顺序派发,
   所以订单回报一定先到;脚本一拿到拒单回报就去翻日志,日志还没入队 → 误记成"(无错误日志)"。
   已加 `Collector.wait_error()`:拿到终态后再等错误日志到达(最多 5 秒)。
   实测间隔:发单 15:54:12.973 → 错误日志 15:54:13.000,约 **27 毫秒**;
   `guard_rule` 的 `ERROR_WINDOW=3s` 与 `reject_classify_delay=1.5s` 对这个间隔绰绰有余
   (运行手册第 5 节第 2 项已回填)。

5. **脚本"跑完了但不退出"**:`main_engine.close()` 会 join CTP 原生线程,4097 断连风暴下可能长时间不返回。
   已改为限时关闭(后台线程 + 10 秒上限),并在 `__main__` 里用 `os._exit` 兜底结束进程。

6. **交易时段内跑采集可能留下持仓**(脚本原本宣称"所有委托都不会成交"):
   "非交易时段开仓"和"超大手数"两个场景用的是**合法价格**,在交易时段内是**可能成交**的。
   已加 `in_trading_session()` 判定:时段内跳过时段场景,并把所有合法价格改成越界价(不可能成交),
   跑完再主动查一次持仓,发现非零持仓就告警并以非零码退出。

7. **价格没对齐最小变动价位**:玉米的 price_tick=1,而"价格超出涨跌停"场景用了 `2195*1.3=2853.5`,
   不是 tick 的整数倍,CTP 会按"价格非法"拒单——测到的就不是想测的场景。已统一用 `round_to` 对齐。

## 第二轮 codex 审查(2026-11-10)追加修的缺陷

| # | 缺陷 | 影响 | 处理 |
|---|---|---|---|
| 8 | **只靠 `--confirm-simnow` 布尔开关挡不住"配置写错"** | 期货公司生产 API 与 SimNow 用同一个"柜台环境=实盘",布尔开关点错了就会连上真券商 | 加 SimNow 官方地址白名单 `SIMNOW_TD_ADDRESSES`,不在表内直接拒绝连接;确有别的模拟环境用 `--allow-any-address` 强制放行并打警告 |
| 9 | **场景之间的错误会串味** | 上一个场景的旧错误离本次发单更近,会被误当成这次的拒单原因,污染采集表 | `Collector.error_index()` 记下当前条数,`error_near/wait_error` 带 `since` 参数,只在本次新增的错误里找 |
| 10 | **"无持仓时平仓"场景可能真的平掉用户的持仓** | 采集脚本会顺手毁掉账户上的仓位 | 发单前 `symbol_has_position()` 查持仓,账户上有任何持仓就中止(退出码 5);查询必须**等满整个窗口**(默认 15 秒),否则 CTP 异步到达的持仓回报会被漏掉、误判成空仓;交易连接断开(查不准)同样中止 |
| 11 | **早退路径不关引擎** | 脚本挂住不退出 | `main()` 用 `try/finally` 统一走 `close_engine()`;采集主体拆到 `_collect()` |
| 12 | **事件线程写列表、主线程读** | 读到半个状态 | `Collector` 加锁,读取走快照 |
| 13 | **多网关时错误会张冠李戴** | 拿 A 网关的错误解释 B 网关的废单 | `_errors` 记来源网关,`_error_text_near(ts, gateway_name)` 按网关过滤并优先取废单回报**之后**到达的日志 |
| 14 | **交易所级废单的原因拿不到** | CTP 的交易所拒单走 `onRtnOrder`,原因在 StatusMsg 里,日志措辞是"委托 X 状态更新，{原因}"(`vnpy_ctp/gateway/ctp_gateway.py:713-719`),**不经过** `onRspOrderInsert` → 原因永远是"未知"→ 一律按硬拒绝 → 平仓单被提前升级为人工处理 | `REJECT_LOG_MARKERS` 加入 `"状态更新"` 措辞 |
| 15 | **发单前查持仓的窗口可能不够** | CTP 的持仓回报是异步的,且对空账户**不推送任何持仓事件**——"没收到回报"既可能是真空仓也可能是回报没到 | 查询改为**等满整个窗口并查两轮**(默认 15 秒 + 7.5 秒),任一轮看到持仓就中止 |
| 16 | **交易时段窗口未覆盖 CFFEX** | 股指/国债 13:00 开,脚本若用合法价发"非交易时段开仓"场景,可能成交 | 下午盘起点由 13:30 提前到 13:00(保守取并集) |
| 17 | **`--allow-any-address` 防呆不足** | 操作者可能因为连不上就随手加上这个开关 | 帮助文本与警告改为明确提示"可能连上真实资金账户" |
